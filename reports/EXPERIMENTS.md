# 单变量优化实验

所有表格都来自同一份 HiDevLab 910C 分配、同一 challenge 提交、同一完整 Seed-TTS
英文数据、seed=0、并发 1、2 个完整语音 warmup 和 32 个计时请求。以下对比均为
严格 `c1/n32`；`baseline_repeat` 是本轮候选实验的共同基线，不与冷启动或快速
4 请求 smoke 结果混用。环境快照见 `evidence/environment/`；该记录不是主办方的
独立认证。

本地 benchmark 中，TTFT 是请求到首个有效文本 token，TTFP 是请求到首个音频包，
RTF 是音频生成计算耗时与音频时长之比，E2E 是请求到完整响应结束，吞吐为完成请求
数除以矩阵墙钟时间（req/s）。最终赛事起止点仍以主办方脚本为准。

## 实验 1：`codec_chunk_frames 25 → 20`

原始 JSON：

- 基线：`results/performance/baseline_repeat_full_c1_n32.json`
- 候选：`results/performance/codec20_full_c1_n32.json`

| 指标 | `baseline_repeat`（25） | `codec20` | 候选相对变化 |
|---|---:|---:|---:|
| 完成/失败 | 32 / 0 | 32 / 0 | 一致 |
| Mean TTFT | 318.936767 ms | 312.002400 ms | 改善 2.17% |
| Mean TTFP | 1021.933432 ms | 953.873700 ms | 改善 6.66% |
| Mean RTF | 0.471207 | 0.499628 | **恶化 6.03%** |
| Mean E2E | 2000.559246 ms | 2125.212800 ms | **恶化 6.23%** |
| 吞吐 | 0.499764 req/s | 0.470459 req/s | **恶化 5.86%** |
| 音频总时长 | 139.0 s | 139.0 s | 一致 |

结论：`codec20` 的 TTFP 更低，但赛事核心 RTF、E2E 和吞吐同时退化，因此淘汰，
不作为最终默认配置。现有结果能证明该配置存在 TTFP/RTF 权衡；未做 profiler
归因前，不把退化原因写成已验证结论。

## 对齐三档请求矩阵：请求成功与尾延迟

`steps9` 进一步跑完了与赛事配置对齐请求数、并发数和主要参数的 `c1/n32`、
`c4/n64`、`c8/n128` 本地矩阵。三档共 224 个计时请求均成功、0 失败。原始结果位于
`results/performance/steps9_repeat_c1_n32.json`、
`steps9_matrix_c4_n64.json` 和 `steps9_matrix_c8_n128.json`。

本次没有直接执行主办方正式 pytest harness，因此这里的“对齐”不代表等同官方
评测环境。224/224 只说明请求级完成，不等于 chunk 连续性或尾延迟稳定。

下表括号为相对官方配置文件内参考值的变化；对时延和 RTF，负数表示更低；对
吞吐，正数表示更高。由于官方参考值不是本机同次运行，表格只能用于矩阵级定位，
不能替代前述同机严格 A/B。

高并发下候选仍能降低 RTF 和 E2E，并提升吞吐；但 `c8/n128` 的 TTFT/TTFP

当前结果尚未覆盖官方 single-chunk latency 分布、NPU/AICore/HBM 利用率采样、
长时间稳定性和多 session 调度；这些项目不能从请求级 JSON 推断。

## 质量检查：32 条配对 WER 代理评测

原始结果：`results/accuracy/whisper_ab_c1_n32.json`。

对上述性能测试中相同的 32 条 Seed-TTS 英文样本，分别保存 `baseline_repeat`
和 `steps9` 的完整输出音频，并使用校验过 SHA-256 的 OpenAI Whisper large-v3
checkpoint 做离线配对转写。文本采用 challenge 中相同的标点清理与 WER
归一化逻辑。

| 指标 | `baseline_repeat` | `steps9` | 差值 |
|---|---:|---:|---:|
| 完成/失败 | 32 / 0 | 32 / 0 | 一致 |
| Mean WER | 1.071238% | 1.071238% | 0.000000 个百分点 |
| Median WER | 0% | 0% | 0 |
| WER 不同的样本数 | - | - | 0 / 32 |
| 原始转写文本不同的样本数 | - | - | 1 / 32（仅句末标点） |

这个结果说明 `steps9` 在本次固定样本上没有造成可见的代理 WER 退化。需要明确：
该脚本使用 OpenAI Whisper 实现，而官方 challenge 评测使用其指定脚本和运行环境；
因此 JSON 内也显式记录了 `official_protocol: false`。它是采用候选前的本地质量
门禁，不得写成“官方 WER 已通过”。

## 质量检查：32 条配对 ASV 代理评测

原始结果：`results/accuracy/asv_ab_c1_n32.json`。

评测使用 seed-tts-eval 固定提交中的 WavLM-large + ECAPA 结构及发布的
`wavlm_large_finetune.pth` 权重，对每条 prompt WAV 与基线/候选输出分别计算
余弦相似度。checkpoint SHA-256、代码提交、模型加载键检查、样本明细和失败数均
写入 JSON。

审计修复后的严格 v2 脚本又完整复跑一次，32/32、0 失败且数值完全一致；原始结果
已纳入 `results/accuracy/asv_ab_c1_n32_strict.json`，运行
指纹为 `97bb7c4af9ead07bf1c94aff9093b0f669866036d5d23663a0a80f763b5485dc`。
它绑定 checkpoint、meta、锁定源码和 96 个输入 WAV 的内容哈希。使用旧进度文件
做负向测试时按预期返回 1 并拒绝恢复，避免跨候选静默串用结果。

| 指标 | `baseline_repeat` | `steps9` | 差值 |
|---|---:|---:|---:|
| 完成/失败 | 32 / 0 | 32 / 0 | 一致 |
| Mean similarity | 0.02345999 | 0.02296496 | -0.00049502（-2.11%） |
| Median similarity | 0.01554724 | 0.01793795 | +0.00239071 |
| 候选更高/更低 | - | - | 17 / 15 对 |
| 配对均值差 95% CI | - | - | [-0.00447, 0.00348] |
| 配对 t / Wilcoxon p 值 | - | - | 0.801 / 0.875 |

在这一未校准 CPU proxy 上，32 对样本的配对差异没有统计显著性，但这既不是
“证明二者等价”，也不能作为 ASV 精度门禁。更重要的是，
官方 `cal_sim.sh` 硬编码 CUDA，而当前 910C 镜像的 Python 3.12 / PyTorch 2.10
无法直接复现其历史 s3prl 0.3.1 / fairseq / PyTorch 0.9 依赖栈。本脚本绕过
s3prl 的全量导入，在 CPU 上直接加载相同 WavLM/ECAPA 代码和权重。因此绝对
similarity 数值不可与赛事 ASV `>= 0.689` 门槛比较，只能作为同样本 A/B
方向检查；JSON 中显式记录 `official_protocol: false`。

## 当前采用决定

`codec20` 淘汰；`steps9` 完成了同机性能复测、三档请求矩阵和配对 Whisper proxy
WER 检查，未校准 ASV proxy 的配对差异也没有统计显著性，因此作为当前提交候选。
这不是官方精度准入结论。它减少一次声学
生成迭代并改变生成数值路径，必须保留一键回退到 `baseline_minicpmo_4_5.yaml`
的能力。主办方正式 WER/ASV 未跑之前，不宣称官方精度通过；`c8/n128` 的
TTFT/TTFP 退化也必须保留在最终报告中。
